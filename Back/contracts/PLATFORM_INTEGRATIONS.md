# Контракт интеграций, календаря и уведомлений

Все пути начинаются с `/api/v1`. Нужна действующая сессия. Изменения требуют `Origin` приложения и `X-CSRF-Token`. Метка **I** означает обязательный `Idempotency-Key` длиной 8–160 символов. Ответы — `{data: ...}`. Секреты и адреса подключений задаются на сервере; через API нельзя указать произвольный URL назначения.

## Календарь и личные уведомления

| Метод и путь                         | Контракт                                                                          |
| ------------------------------------ | --------------------------------------------------------------------------------- |
| `GET /notifications?page=1&limit=30` | Только уведомления связанного сотрудника; limit 1–100                             |
| `POST /notifications/:id/read`       | Отметить своё уведомление прочитанным; чужое недоступно                           |
| `GET /notification-preferences`      | `{inApp:true,messenger:false,reminders:true}` по умолчанию                        |
| `PUT /notification-preferences`      | `{inApp:boolean,messenger:boolean,reminders:boolean}`                             |
| `GET /calendar`                      | `{filename:"career-quest.ics",contentType:"text/calendar",content,dateOnly:true}` |

Календарь содержит только собственные зарегистрированные и начатые активности. Дата берётся из сессии, затем из due date, затем из даты записи. В исходном датасете нет времени начала и часового пояса занятия: ICS использует события на целый день и не выдумывает время.

Фиксированные уведомления о наставничестве, благодарностях, наградах, очереди и напоминаниях создаются на `employees.preferred_language` (`ru`, `kk`, `en`). Название мероприятия в напоминании использует утверждённый перевод, если он есть; иначе сохраняется исходное название. Пользовательские тексты не переводятся автоматически. Ошибки API имеют стабильные коды для локализации на frontend.

Фоновый worker создаёт напоминания на ближайшие семь дней **по дате сессии или due date**, а не по дате регистрации. Активности без обеих дат не создают ложные напоминания. Повторные проходы worker не дублируют уведомление на одну дату. Календарная точка отсчёта — дата синтетического датасета; при его замене это правило нужно согласовать с корпоративной системой времени.

## Административные настройки

Все endpoints `/integrations` доступны только `admin`.

| Метод и путь                                   | Контракт                                                                                                                    |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `GET /integrations`                            | Ключи настроенных подключений, признаки worker/SSO, `messengerTargetKey`, статус NVIDIA `deferred`; секреты не возвращаются |
| `GET /integrations/webhooks`                   | Подписки, темы, targetKey, active                                                                                           |
| `POST /integrations/webhooks` **I**            | `{name,targetKey,topics:[...]}`                                                                                             |
| `PATCH /integrations/webhooks/:id`             | `{active:boolean}`                                                                                                          |
| `GET /integrations/deliveries`                 | Последние 100 доставок, статусы, попытки, следующая попытка; тексты ошибок внешней системы не раскрываются                  |
| `GET /integrations/identities?providerKey=...` | До 1000 соответствий внешних и внутренних ID                                                                                |
| `PUT /integrations/identities` **I**           | `{providerKey,entityType:"employee"                                                                                         | "event",externalId,localId}`                          |
| `DELETE /integrations/identities` **I**        | `{providerKey,entityType:"employee"                                                                                         | "event",externalId}`; удалить устаревшее соответствие |

Поддерживаемые темы: `goal.changed`, `participation.completed`, `event.published`, `notification.created`. Подписка создаётся только для `targetKey`, уже определённого в серверном allowlist.

```dotenv
# Пример конфигурации; замените фиктивный URL и секрет своими.
INTEGRATION_TARGETS_JSON={"messenger_relay":{"url":"https://relay.example.org/career-quest","secret":"replace-with-a-long-random-shared-secret"}}
MESSENGER_TARGET_KEY=messenger_relay
WORKER_DELIVERY_ENABLED=false
```

Пустой `INTEGRATION_TARGETS_JSON` равнозначен `{}`. Разрешены HTTPS URL без встроенных логина/пароля и fragment. HTTP redirect при отправке запрещён. `WORKER_DELIVERY_ENABLED=false` оставляет фоновую внешнюю доставку выключенной.

## Подключение корпоративного мессенджера

Реализован протокол через серверный relay. Реальный Slack/Teams/другой бот и его корпоративные credentials должны быть настроены владельцем инфраструктуры; приложение не создаёт вымышленные аккаунты и адресатов.

1. Подготовьте HTTPS relay, принимающий подписанные webhooks по контракту ниже и отправляющий личное сообщение указанному `recipientId`.
2. Добавьте URL и общий секрет в `INTEGRATION_TARGETS_JSON`, укажите его ключ в `MESSENGER_TARGET_KEY`.
3. Администратор создаёт одну активную подписку с `targetKey` этого канала и темой `notification.created`. Для одного targetKey разрешена одна активная подписка на эту тему, чтобы не создавать двойные личные сообщения.
4. Через `PUT /integrations/identities` сопоставьте сотрудника и ID личного получателя: `providerKey=MESSENGER_TARGET_KEY`, `entityType="employee"`, `localId` — ID сотрудника, `externalId` — ID в мессенджере. Это должен быть подтверждённый **личный получатель**, а не публичный канал. Для одного сотрудника требуется ровно одно соответствие внутри этого provider; неоднозначные соответствия не отправляются.
5. Сотрудник сам включает `messenger:true` через свои настройки. Канал выключен по умолчанию. При включении фиксируется серверное время согласия, поэтому старые уведомления не рассылаются задним числом.
6. Включите `WORKER_DELIVERY_ENABLED=true` для worker после проверки настройки relay. Worker ставит новые непрочитанные уведомления в outbox и доставляет их через подписку.

`enqueueMessengerNotifications` не обращается к сети. SQL-транзакция блокирует выбранные уведомления через `FOR UPDATE SKIP LOCKED`, создаёт outbox и отмечает `messenger_enqueued_at` атомарно. Два worker не ставят одно уведомление в очередь дважды.

Событие `notification.created` доставляется **только** подписке, у которой `targetKey` совпадает с `payload.targetKey`. Подписчики на другие каналы не получают личные уведомления. Непосредственно перед отправкой повторно проверяются согласие, непрочитанность, текущий recipient mapping и настройка targetKey. Изменение адресата, отключение канала, прочтение уведомления или отказ от напоминаний отменяют соответствующую ожидающую доставку со статусом `suppressed`. Отменённая доставка не возобновляется после повторного включения согласия.

Пример тела для relay:

```json
{
  "id": "uuid-of-outbox-event",
  "topic": "notification.created",
  "payload": {
    "channel": "messenger",
    "targetKey": "messenger_relay",
    "notificationId": "uuid-of-notification",
    "employeeId": "E0001",
    "recipientId": "confirmed-private-recipient-id",
    "kind": "learning.reminder",
    "title": "Название учебной активности",
    "body": "Предстоящая учебная активность",
    "link": "/events/EV_005"
  },
  "createdAt": "2026-09-23T12:00:00Z"
}
```

Relay должен отображать `title`/`body` как текст, не исполнять разметку или упоминания как команды, а относительный `link` открывать относительно разрешённого URL Career Quest. Содержимое уведомлений передаётся только в канал, на который сотрудник согласился.

## Подпись, идемпотентность и повторная доставка

Каждый webhook содержит:

- `Idempotency-Key`: неизменный UUID доставки;
- `X-Career-Quest-Timestamp`: Unix timestamp в секундах;
- `X-Career-Quest-Signature`: hex HMAC-SHA256 общего секрета от строки `timestamp + "." + rawBody`.

Получатель проверяет подпись по исходным байтам JSON, допустимый возраст timestamp и сохраняет `Idempotency-Key` для защиты от повторного выполнения. Сравнение подписи должно выполняться с постоянным временем. Отвечайте `2xx` после надёжного принятия события; повтор с тем же ключом должен также возвращать успех без повторного сообщения.

Доставка имеет семантику **как минимум один раз**: сбой после принятия на внешней стороне может потребовать повтор. Worker делает до пяти попыток с увеличением задержки; таймаут одной отправки — 5 секунд. Статусы: `pending`, `sending`, `delivered`, `failed`, `suppressed`. Lease и номер попытки не позволяют запоздавшему worker перезаписать результат более новой попытки. После исчерпания пяти попыток администратор видит `failed` и должен разобраться с подключением; бесконечные повторы не выполняются.

## IT/HR-заявки

| Метод и путь                | Контракт                                                                      |
| --------------------------- | ----------------------------------------------------------------------------- |
| `GET /tickets`              | Только заявки текущей учётной записи                                          |
| `POST /tickets` **I**       | `{providerKey,title,description}`; `201` после подтверждения внешнего сервиса |
| `POST /tickets/:id/refresh` | Получить свежий статус своей заявки                                           |

Для ticket provider allowlist URL используется как базовый endpoint. Сервер отправляет:

- `POST <url>` с `{title,description,employeeId}`, `Authorization: Bearer <secret>` и стабильным `Idempotency-Key`;
- получает JSON `{id:string,status:string}`;
- запрашивает состояние через `GET <url>/<urlencoded-id>` и ожидает `{id,status}` с тем же ID.

Внешний сервис обязан поддерживать идемпотентность POST: локальная транзакция не может отменить уже созданную внешнюю заявку при сетевом сбое. При неподключённой системе возвращается `503 INTEGRATION_NOT_CONFIGURED`; ID и статус заявки не выдумываются. Внешние запросы выполняются только после явного действия пользователя и при наличии серверной конфигурации.

## Импорт LMS/HRIS

### `POST /integrations/import`

Только `admin`. Для этого endpoint ключом идемпотентности служит пара `providerKey + messageId` в теле:

```json
{
  "providerKey": "lms",
  "messageId": "source-message-unique-id",
  "history": [
    {
      "record_id": "provider-qualified-record-id",
      "employee_id": "external-employee-id",
      "event_id": "external-event-id",
      "date": "2026-09-30",
      "due_date": null,
      "status": "completed",
      "completion_pct": 100,
      "score": 85,
      "feedback_rating": 5,
      "assigned_by": "self"
    }
  ]
}
```

Поля истории должны соответствовать общему контракту импорта. `record_id` должен быть глобально уникальным среди источников; используйте namespace провайдера. Для `employee_id` и `event_id` требуются предварительные соответствия через `/integrations/identities`. `employees` может содержать нормализованный пакет профилей по основному контракту импорта. CSV в интеграционном endpoint не принимается — для него есть обычный импорт.

Обработка:

1. Атомарный запрос фиксирует receipt с SHA-256 тела и lease на 10 минут; connection немедленно освобождается.
2. Если такое тело уже обработано, возвращается сохранённый результат. Если ID повторён с другим телом — `409 MESSAGE_CONFLICT`.
3. Пока lease действует, конкурентный повтор получает `409 IMPORT_IN_PROGRESS` и может повторить запрос позже. Он не занимает connection в ожидании другого импорта.
4. После сопоставления ID нормализованный пакет сохраняется в receipt, затем передаётся обычному атомарному SQL-импорту. Повтор после сбоя использует тот же пакет даже если администратор успел изменить соответствия.
5. После commit результат фиксируется только владельцем текущего lease token. Если процесс завершился между commit и сохранением receipt, повтор после истечения lease распознаёт уже импортированный пакет по его hash и не дублирует данные.
6. При обычной ошибке lease освобождается сразу. При аварийном завершении повтор разрешён через 10 минут. Исправленный пакет получает новый `messageId`; одинаковый ключ с новым содержимым не перезаписывает историю.

## Проверки

В `tests/platform.test.ts` используются только фиктивные URL и mock `fetch`: реальные сообщения, заявки или платные запросы тестами не создаются.

Проверяются подписи, повтор доставки, приватность уведомлений, даты календаря/напоминаний, согласие и адресат мессенджера, отсутствие межканальной утечки, конкурентная постановка outbox, отзыв согласия, смена адресата, стабильные ID заявок, права администратора и импорт. Тест импорта запускает 12 конкурентных повторов при заблокированном основном importer и подтверждает доступность pool; отдельно имитируется сбой после commit с последующим восстановлением по сохранённому пакету.

```bash
cd Back
TEST_DATABASE_URL=postgresql://career_quest:career_quest_local_only@localhost:5433/career_quest \
  npx tsx --test tests/platform.test.ts
```

База в примере — локальный демонстрационный PostgreSQL из Compose. Все SQL-проверки создают отдельную случайную схему и удаляют её после выполнения.
