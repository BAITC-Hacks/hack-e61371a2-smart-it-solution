# Контракты backend для параллельной разработки Front

## Подключение Front

Frontend вызывает относительные адреса `/api/v1/...`. В локальном Vite proxy направляет их на `http://127.0.0.1:3001`. При таком запуске backend должен иметь `APP_ORIGIN=http://localhost:5173`; браузер открывает именно этот адрес. В Docker приложение открывается на `http://localhost:8080` с соответствующим `APP_ORIGIN`.

1. При старте вызвать `GET /auth/me` с cookie. `401` означает отсутствие активного сеанса.
2. Для входа вызвать `POST /auth/login`; ответ содержит `{user,csrfToken}` и устанавливает HttpOnly cookie `cq_session`. Cookie хранит браузер; JavaScript её не читает.
3. Для каждого авторизованного `POST/PUT/PATCH/DELETE` передавать `X-CSRF-Token`. Origin устанавливает браузер; он должен совпадать с `APP_ORIGIN`.
4. Для операций с `x-idempotency-required:true` в OpenAPI передавать `Idempotency-Key`. Создавать один ключ на пользовательское действие и сохранять его для повтора именно этого действия.
5. После выхода, `401` или смены пользователя очищать профиль, диалоги и кеш предыдущего пользователя.

SSO-start и login не требуют CSRF сеанса до входа, но требуют корректный Origin. OIDC callback — `GET`, устанавливает cookie и возвращает `303`; это единственный описанный маршрут, не возвращающий обычный JSON-конверт успеха.

Пример завершения активности:

```ts
// Ключ создаётся один раз для нажатия, повтор запроса использует тот же ключ.
const completionKey = crypto.randomUUID();

async function completeParticipation(id: string, csrfToken: string) {
  const response = await fetch(`/api/v1/participations/${encodeURIComponent(id)}/complete`, {
    method: "POST",
    credentials: "same-origin",
    headers: {
      "Content-Type": "application/json",
      "X-CSRF-Token": csrfToken,
      "Idempotency-Key": completionKey,
    },
    body: JSON.stringify({}),
  });
  const payload = await response.json();
  if (!response.ok) throw payload.error;
  return payload.data;
}
```

Не передавайте ключи OpenAI, NVIDIA или интеграций во Front, `VITE_*`, браузерные запросы либо Git. Front обращается только к Back.

## Ответы и ошибки

Успех:

```json
{"data": {}, "meta": {"total": 200, "page": 1, "limit": 30}}
```

`data` может быть объектом, массивом или `null`; `meta` передаётся только там, где нужен. Ошибка:

```json
{"error": {"code": "EVENT_INELIGIBLE", "message": "Мероприятие недоступно", "requestId": "UUID"}}
```

`details` необязателен и зависит от ошибки. `X-Request-Id` присутствует в HTTP-ответе. Интерфейс опирается на стабильный `code`, а не сравнивает текст сообщения.

| Статус | Реакция UI |
| --- | --- |
| 400 | Показать ошибки полей или несовместимые параметры. |
| 401 | Очистить приватный кеш и открыть вход. |
| 403 | Скрыть недоступное действие; сервер всё равно проверяет права. |
| 404 | Запись отсутствует или больше недоступна текущему пользователю. |
| 409 | Обновить актуальные данные: конфликт версии/состояния, полная сессия, занятый диалог либо конфликт ключа. Не повторять автоматически с новым ключом. |
| 413 / 422 | Показать лимит загрузки либо отчёт валидации импорта. |
| 429 | Сообщить о лимите; сохранить введённый текст/форму. |
| 502 / 503 | Показать недоступность или отсутствие настройки внешнего сервиса. |

Не все ответы автоматически преобразуются в camelCase. Карьерные DTO в основном используют camelCase; редактор путеводителя и некоторые административные списки возвращают SQL-поля `topic_id`, `applies_when`, `created_at` и т. п. Их точные поля указаны в OpenAPI и модульных договорах. Дополнительные поля ответа разрешены там, где сервер возвращает расширяемые строки; не считайте неизвестное поле ошибкой.

## Права доступа

| Роль | Область |
| --- | --- |
| `employee` | Собственный профиль, цель и участие; личные планы, диалоги, задания и награды. |
| `manager` | Собственный профиль и чтение прямой команды; изменение чужой цели/участия запрещено. Создание командных активностей для своей команды. |
| `hr` | Организационная аналитика, профили, мероприятия, корректировки истории, путеводитель и разрешённая модерация. |
| `admin` | HR-возможности плюс аккаунты, аудит, импорт, настройки наград, интеграции и бюджет AI. |

Роль доступа `manager/hr/admin` не выводится из профессии или грейда датасета. `/me/*` требует связанного `employeeId`, включая аккаунт HR/admin. Личные диалоги, достижения, кошельки и планы не становятся общедоступными для HR из-за роли. Для некоторых ресурсов проверяется согласие, принадлежность диалогу, статус публикации, отдел либо участие в команде; эти условия записаны в `x-access-scope`.

## Состояния, которые нужно показать во Front

- У Lead без цели: выбор направления, без выдуманного следующего грейда.
- У предварительной цели: `inferred:true`; пользователь ещё не принял её.
- У рекомендаций: `stale`, `source`, `emptyReason`, причины исключений, ожидаемые приросты. ИИ может быть отключён; базовый расчёт при этом работает.
- У сессии: свободные места, очередь, дата и причина недоступности. `waitlisted` не означает запись с занятым местом.
- У плана: `requiresRefresh`, `goalChanged`, `version`. Пересчёт требует `expectedVersion`.
- У статьи: опубликованность, `synthetic`, дата проверки/срок действия. Истёкшая или закрытая статья недоступна сотруднику.
- У наград/интеграций: выключенные правила или отсутствие подключения. Не рисовать вымышленные баллы, номера заявок и внешнюю доставку.

После завершения активности обновить профиль, навыки, прогресс, историю и рекомендации. После смены цели обновить цель, прогресс и рекомендации; существующий план предлагает пересчёт. GET-запросы не сохраняют бизнес-изменения.

Учебные даты в этом кейсе считаются относительно `dataset.asOfDate` (исходный набор — 2026-10-01). Системное время используется для сессии входа, аудита, лимитов AI, срока статей и суточных ограничений. Дата прохождения в старой истории уже включена в baseline, если она не позже `lastReviewDate`.

## Проверка интеграции перед PR

1. Войти каждой ролью, открыть доступные страницы, проверить 401/403/404 и очистку данных при смене пользователя.
2. Установить цель → получить рекомендации → записаться на допустимое самостоятельное обучение → завершить → увидеть изменение прогресса.
3. Повторить запрос завершения с тем же ключом: нового прироста нет.
4. Проверить полную сессию/очередь, отсутствие подходящих активностей, Lead без цели и конфликт версии плана.
5. Открыть утверждённую демо-статью, задать вопрос помощнику при выключенном платном AI, показать ссылки и синтетический статус материалов.
6. Проверить формы HR/админа с реальным backend. Моки помогают верстать, но не подтверждают права, транзакции и серверную валидацию.

Работайте в собственной ветке `codex/...`, меняйте согласованную область `Front/**`, публикуйте готовые части через PR. Изменение контракта согласовывайте через отдельное предложение; не дублируйте серверные расчёты навыков и доступа в интерфейсе.
