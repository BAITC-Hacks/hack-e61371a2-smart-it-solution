# Опциональный семантический поиск путеводителя

Реализует GUIDE-X-03. Модуль `src/semantic.ts`, миграция `008_semantic.sql`. По умолчанию выключен. Использует обычный SQL через `pg`: vectors хранятся в `double precision[]`, cosine similarity рассчитывается в Node.js. Дополнительное расширение PostgreSQL не требуется.

В режиме разработки и в тестах реальные OpenAI-запросы не выполнялись. Все проверки провайдера используют mock responses. Реальное качество на корпоративных текстах нужно измерить после настройки модели и подготовки контрольных вопросов.

## Подключение

В дополнение к общим настройкам AI необходимы:

```dotenv
AI_ENABLED=false
AI_EMBEDDING_MODEL=
AI_EMBEDDING_USD_PER_MILLION=
```

`OPENAI_API_KEY` остаётся только на сервере. Название embedding-модели в коде не задано: администратор выбирает доступную в своём проекте модель и указывает проверенную положительную цену за миллион входных токенов. Пока `AI_ENABLED` не равен `true`, отсутствует модель, ключ или положительная цена, пользовательский поиск возвращает обычные SQL-результаты.

Провайдер вызывается через `POST https://api.openai.com/v1/embeddings` с `model`, массивом `input` и `encoding_format:"float"`. Ответ проверяется по модели, индексам элементов, размерности, конечным значениям вектора и usage. Формат API подтверждён по [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/embeddings) и [справочнику Create embeddings](https://developers.openai.com/api/reference/ruby/resources/embeddings/methods/create).

Включение `AI_ENABLED` само по себе не активирует семантический поиск: дополнительно требуется положительная контрольная оценка и явный запрос администратора на включение.

## Порядок запуска

1. Подготовить и опубликовать утверждённые актуальные статьи. Для разрешённых к передаче провайдеру материалов установить `aiAllowed:true`.
2. Настроить embedding-модель, её цену и общие лимиты расходов AI.
3. Администратору проиндексировать статьи пачками не более 10 ID.
4. Подготовить 10–30 различных реальных рабочих вопросов и правильные ID статей. Вопросы и ожидаемые ответы задаёт администратор; система их не выдумывает.
5. Запустить сравнение SQL-поиска и семантического поиска на одних и тех же вопросах.
6. При успешной оценке включить функцию, передав ID сохранённого сравнения.
7. Пользователи получают семантический поиск по новым произвольным фразам. Новые query embeddings оплачиваются в рамках общего бюджета, повторные нормализованные вопросы используют кеш.

Любое изменение актуального набора статей, их прав доступа, актуальности, настроек тем или содержимого индекса делает прежнюю оценку непригодной для активации. Пользовательский поиск автоматически возвращается к SQL до нового сравнения и включения.

## API

Все пути ниже начинаются с `/api/v1`. Нужна сессия; POST проверяет `Origin` и `X-CSRF-Token`. Ответы находятся в `{data: ...}`.

### `POST /guide/semantic-search`

Доступен авторизованным пользователям в пределах их прав на статьи.

```json
{ "q": "Куда обратиться, если не работает рабочий доступ?", "locale": "ru" }
```

`q`: 2–300 символов. `locale`: `ru`, `kk` или `en`; по умолчанию `ru`. Для активного семантического поиска нужен `Idempotency-Key` длиной 8–160 символов. При выключенной функции или устаревшем индексе бесплатный SQL fallback работает и без этого заголовка.

Ответ:

```json
{
  "source": "semantic",
  "fallbackReason": null,
  "articles": [
    {
      "id": "article-uuid",
      "topicId": "topic-uuid",
      "locale": "ru",
      "title": "Название",
      "summary": "Краткая инструкция",
      "version": 1,
      "synthetic": false,
      "score": 0.86
    }
  ],
  "usageIds": ["ai-usage-uuid"]
}
```

Возвращается максимум три статьи. Поле `score` есть только у семантических результатов. Тело инструкции можно получить через существующий endpoint статьи с повторной проверкой прав.

Fallback возвращает `source:"sql"`, результаты существующего `searchGuide` и причину, например `DISABLED`, `NOT_ENABLED_OR_STALE`, `UNINDEXED`, `AI_BUDGET_LIMIT`, `AI_RATE_LIMIT`, `EMBEDDING_UNAVAILABLE`, `INDEX_CHANGED`. Сбой внешней модели не блокирует путеводитель.

### `POST /admin/semantic/index`

Только `admin`, обязательный `Idempotency-Key`.

```json
{ "articleIds": ["article-uuid-1", "article-uuid-2"] }
```

Принимает 1–10 уникальных UUID. Индексируются только опубликованные, утверждённые, неистёкшие `ai_allowed` статьи активных тем. Черновик, архивная или неразрешённая для AI статья отклоняется до обращения к провайдеру.

Ответ: `{indexed:[{articleId,revisionHash,charactersIndexed,truncated}],model,corpusHash,indexHash,usageId}`.

Для каждого материала индексируется очищенный фрагмент: название, краткое содержание, условия применения, шаги и начало основного текста, суммарно **до 2000 символов** после очистки. У длинных инструкций индекс описывает начальный фрагмент; полная статья остаётся доступной в обычном путеводителе. Это ограничение видно по `charactersIndexed` и признаку исходного длинного текста `truncated` и учитывается реальной оценкой качества. Увеличение размера или переход к нескольким фрагментам требует отдельной оценки расходов и качества.

После ответа провайдера перед сохранением повторно проверяются версия/актуальность статьи и полномочия администратора. Если статья изменилась или была архивирована, результаты не записываются как актуальный индекс. Затраченная сумма остаётся отражённой в журнале AI.

### `POST /admin/semantic/evaluate`

Только `admin`, обязательный `Idempotency-Key`.

```json
{
  "queries": [
    {
      "q": "Рабочий вопрос с ожидаемым ответом",
      "locale": "ru",
      "expectedArticleIds": ["article-uuid"]
    }
  ]
}
```

Пример показывает формат одного элемента; запрос должен содержать **10–30 вопросов**, минимум 10 различных фраз после очистки, нормализации регистра и пробелов. Для каждого вопроса задаётся 1–3 уникальных ожидаемых ID. Ожидаемые материалы должны быть доступны администратору в обычном режиме чтения и находиться в актуальном индексе. Все доступные этому пользователю AI-статьи соответствующего языка должны быть проиндексированы.

Для каждого вопроса вычисляется:

`recall@3 = число правильных статей среди первых трёх результатов / число ожидаемых статей`.

Затем рассчитывается средний recall по всему контрольному набору отдельно для SQL и semantic. Оценка проходит только если одновременно:

- имеется минимум 10 различных контрольных вопросов;
- semantic recall@3 **не ниже SQL recall@3**;
- semantic recall@3 **не ниже 0.7**;
- модель, набор материалов и индекс не изменились во время проверки.

Ответ: `{id,model,corpusHash,indexHash,queryCount,sqlRecallAt3,semanticRecallAt3,passed,results,usageIds}`. Каждый элемент `results` содержит очищенный вопрос, язык, ожидаемые ID, фактические ID SQL/semantic и обе метрики. Сравнение сохраняется в БД; клиент не может передать собственные `passed` или значения метрик.

Контрольный набор должен отражать реальные рабочие вопросы и аудиторию. Сам по себе успешный результат на искусственно простых вопросах не доказывает качество для всех подразделений или языков.

### `POST /admin/semantic/enable`

Только `admin`, обязательный `Idempotency-Key`.

```json
{ "enabled": true, "evaluationId": "saved-evaluation-uuid" }
```

Включение повторно проверяет сохранённую оценку, пороги и совпадение текущих `model`, `corpusHash`, `indexHash`. При несоответствии возвращается `409 EVALUATION_REQUIRED`.

Ответ: `{enabled:true,evaluationId,model,corpusHash,indexHash}`. Выключение: `{enabled:false}` без `evaluationId`, доступно даже когда настройки провайдера отсутствуют. После выключения новые поисковые запросы не расходуют бюджет embeddings.

## Права доступа и приватность

- Кандидаты для пользовательского поиска проходят `getGuideArticle` с текущими ролью и подразделением до загрузки их векторов и ранжирования.
- После inference повторно проверяются доступ к возвращаемым статьям, актуальность индекса и состояние учётной записи. Отключение, смена роли или привязки сотрудника во время запроса приводит к `401 AUTH_CONTEXT_CHANGED`.
- Индексация использует административные права управления контентом; обычный пользователь не может запустить индексацию или оценку.
- В embeddings не передаются контакты из справочника, resources, профили сотрудников, карьерная история или идентификатор пользователя. Из разрешённого текста и поисковой фразы удаляются известные имена/ID сотрудников, известные значения контактов, email, номера, ключи и URL.
- AI-разрешение и человеческое согласование содержания остаются обязательными. Очистка не является универсальной системой распознавания всех возможных персональных данных в произвольном тексте.
- В query cache сохраняются hash, модель, язык и вектор; исходные пользовательские фразы там не хранятся. В контрольной оценке сохраняются только очищенные фразы.
- Повтор сохранённого поиска возвращает актуальные разрешённые материалы; содержимое статьи не копируется в receipt и не используется для обхода ACL.

## Расходы, таймауты и повторные запросы

Используется общий durable ledger `ai_usage` через `reserveAiBudget`/`settleAiBudget`. Семантические запросы расходуют тот же проектный и персональный бюджет и те же лимиты частоты, что и помощник. Отдельного неограниченного баланса нет.

До запроса резервируется консервативная верхняя оценка по UTF-8 байтам входа с запасом и явно настроенной цене. Успешный ответ списывает проверенный фактический `usage`; сетевой сбой, timeout или некорректный ответ консервативно списывают резерв. При определённом отказе API до выполнения (например, 401 или 429) резерв освобождается. Неизвестный исход не считается бесплатным.

Платный HTTP-запрос выполняется **вне SQL-транзакции**. В БД сначала фиксируется receipt. Повтор того же ключа не создаёт второй запрос; параллельный повтор получает `409 SEMANTIC_REQUEST_IN_PROGRESS`. Если процесс аварийно завершился, через две минуты receipt считается неопределённым (`SEMANTIC_REQUEST_UNCERTAIN`): автоматического повторного списания по этому ключу нет. Администратор/клиент проверяет результат и бюджет перед явным запросом с новым ключом.

Таймаут провайдера не превышает 8 секунд и учитывает общий `AI_TIMEOUT_MS`. Ответ ограничен 3 MiB, размерность вектора — 4096, число входов одного provider request — 30. Текущая реализация поддерживает до 500 актуальных AI-статей; при превышении пользовательский поиск использует SQL fallback. Для более крупного корпуса нужен отдельный вариант индекса и замер производительности.

## Проверки

`tests/semantic.test.ts` проверяет:

- выключенные и неполные настройки, cosine и recall@3;
- запрет индексации черновиков и `ai_allowed=false`, права администратора;
- очистку имён, employee ID, адресов, телефона и известного контакта;
- общий журнал расходов и свободный pool connection во время запроса даже при `max:1`;
- запрет включения при низком recall, повторную оценку и соответствие модели/индекса;
- произвольные фразы, кеш и отсутствие чужих статей в результатах;
- SQL fallback при ошибке модели или исчерпании бюджета без повторных расходов по ключу;
- отключение учётной записи и архивирование статьи во время inference;
- консервативное списание при некорректном векторе.

```bash
cd Back
TEST_DATABASE_URL=postgresql://career_quest:career_quest_local_only@localhost:5433/career_quest \
  npx tsx --test tests/semantic.test.ts
```

Используется отдельная случайная схема PostgreSQL, удаляемая после тестов. Все provider calls заменены mock; наличие API-ключа для этих проверок не требуется.
