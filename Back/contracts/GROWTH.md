# Развитие и добровольная мотивация: API

Модуль `src/growth.ts`, миграция `005_growth.sql`. Покрывает ROAD-01–06 и GAME-01–05 из ТЗ. Все пути ниже начинаются с `/api/v1`. Внешний HTTP-сервер проверяет сессию, Origin и CSRF для изменений. Ответы обёрнуты в `{ "data": ... }`.

`me` означает сотрудника, связанного с текущей учётной записью. HR/администратор без профиля сотрудника получает `403 EMPLOYEE_REQUIRED`. Личные планы, задания, достижения, переписка наставничества и кошелёк доступны только владельцу. HR не получает отдельный endpoint для просмотра приватных достижений.

## Общие правила

- Все изменяющие запросы передают `X-CSRF-Token`. Для endpoint, отмеченных **I**, нужен `Idempotency-Key` длиной 8–160 символов. Повтор ключа с тем же телом возвращает прежний результат, с другим телом — `409 IDEMPOTENCY_CONFLICT`.
- Поля JSON проверяются строго. Неизвестные поля не принимаются. UUID имеют стандартный формат.
- Персональные списки ограничены последними 100 записями; поиск коллег возвращает максимум 20 результатов. Список сохраняет историю в БД даже если она не вошла в последние 100 записей.
- Даты учебных планов используют `dataset_batches.as_of_date` — для исходного кейса это 2026-10-01. Реальное серверное время используется для аудита, модерации, суточных лимитов и баллов.
- Никакие endpoints этого модуля не вызывают платный ИИ.

## Предпочтения

| Метод и путь          | Доступ    | Тело / результат                                                                                       |
| --------------------- | --------- | ------------------------------------------------------------------------------------------------------ |
| `GET /me/preferences` | Сотрудник | `{weeklyHours, formats}`; по умолчанию 4 часа и все форматы                                            |
| `PUT /me/preferences` | Сотрудник | `{weeklyHours: 0.5..40, formats: ["online", "offline", "self_paced"]}`; минимум один уникальный формат |

Предпочтение формата повышает приоритет подходящей активности; оно не скрывает другие полезные варианты. Ограничение часов определяет объём и последовательное расписание плана. Изменение предпочтений делает существующий план требующим пересчёта.

## Прогнозы и сравнение целей

### `POST /me/growth/simulate`

```json
{
  "eventIds": ["EV_005", "EV_010"],
  "goal": { "targetRole": "Data Analyst", "targetGrade": "Senior" }
}
```

`goal` необязателен; используется текущая явная или предложенная цель. `eventIds` — 1–30 уникальных идентификаторов в желаемом порядке.

Для каждого шага сервер проверяет активность, текущие роль/грейд, prerequisites, историю, будущую сессию и свободное место. Предыдущие прогнозируемые приросты открывают следующий шаг. Обязательные мероприятия отклоняются. Несовместимый шаг возвращает `409 EVENT_NOT_ELIGIBLE` с причинами. Завершённые неповторяемые мероприятия нельзя использовать повторно.

Результат: `{baselineLevels, projectedLevels, unmetRequirements, steps, persisted:false}`. Шаг содержит `eventId`, `sessionId`, `gains:[{skillId,from,to}]`. Записи участия, навыки и карьерная цель не меняются. Прогноз не гарантирует повышение или наличие места при реальной записи.

### `POST /me/growth/compare`

Тело: `{goals: [{targetRole,targetGrade}, ...], horizonDays: 30|90|180}`. Допустимы 2–4 цели; горизонт по умолчанию 90 дней.

Для каждой цели возвращается отдельный прогноз: доступная последовательность, учебные часы, общий бюджет часов, исходные и ожидаемые уровни, оставшиеся разрывы с признаком критичности. `totalHours` — часы выбранных доступных шагов, а не обещанная полная стоимость достижения цели. Неустранимые текущим каталогом разрывы остаются в `unmetRequirements`.

## Планы на 30/90/180 дней

| Метод и путь                          | Тело                  | Результат                                                             |
| ------------------------------------- | --------------------- | --------------------------------------------------------------------- | ------------------------------------- | ----------------------------- |
| `GET /me/plans`                       | —                     | Список планов владельца                                               |
| `POST /me/plans` **I**                | `{horizonDays:30      | 90                                                                    | 180, goal?:{targetRole,targetGrade}}` | Новый сохранённый план, `201` |
| `GET /me/plans/:id`                   | —                     | Полный план с актуальной отметкой выполненных шагов                   |
| `POST /me/plans/:id/regenerate` **I** | `{expectedVersion:1}` | Пересчёт по текущей карьерной цели, навыкам, каталогу и предпочтениям |
| `POST /me/plans/:id/archive` **I**    | `{expectedVersion:1}` | Архивирование; повторное редактирование архива запрещено              |

План содержит `id`, `employeeId`, `targetRole`, `targetGrade`, `horizonDays`, `startDate`, `status`, `weeklyHours`, `formats`, `baselineLevels`, `projectedLevels`, `unmetRequirements`, `totalHours`, `version`, `goalChanged`, `requiresRefresh`, `steps`.

Шаг содержит `position`, `eventId`, `title`, `sessionId`, `scheduledDate`, `durationHours`, `gains`, `prerequisites`, `alternatives` (до трёх ID альтернатив), `completed`. Выполнение определяется реальной историей сотрудника начиная с даты плана. Запись в план сама по себе не записывает сотрудника на мероприятие и не резервирует место.

Алгоритм рекурсивно находит подготовительные мероприятия, проверяет prerequisites после каждого прогнозируемого шага, уважает роль/грейд, занятые места, время и горизонт. Не создаёт вымышленные курсы для отсутствующих навыков. Циклы без доступной начальной активности оставляют явный незакрытый разрыв.

`goalChanged` показывает отличие от текущей карьерной цели. `requiresRefresh` учитывает также изменение навыков и предпочтений. Интерфейс предлагает `regenerate`; план не перезаписывается незаметно. Изменение каталога проверяется при фактической записи. `expectedVersion` защищает от перезаписи из устаревшей вкладки (`409`).

## Наставничество по обоюдному согласию

| Метод и путь                       | Доступ / тело                                                 |
| ---------------------------------- | ------------------------------------------------------------- | ---------- | ----------- | ------------- |
| `GET /mentors/me`                  | Собственный профиль наставника или `null`                     |
| `PUT /mentors/me`                  | `{headline, skillIds:[...], capacity:1..20, enabled:boolean}` |
| `GET /mentors?skillId=...`         | Опубликованные включённые профили; фильтр необязателен        |
| `GET /admin/mentors`               | HR/admin: очередь профилей на проверку                        |
| `PATCH /admin/mentors/:employeeId` | HR/admin: `{approved:boolean}`                                |
| `GET /me/mentorships`              | Запросы, где сотрудник — автор или выбранный наставник        |
| `POST /me/mentorships` **I**       | `{mentorId, message}`; создаёт `pending`                      |
| `PATCH /me/mentorships/:id`        | `{status:"accepted"                                           | "declined" | "cancelled" | "completed"}` |

Сотрудник сам даёт согласие на публикацию профиля. Изменение профиля сбрасывает утверждение; до повторной проверки он не виден в каталоге. Каталог возвращает только идентификатор, имя, описание, навыки и вместимость добровольно опубликованного профиля.

Только наставник может принять/отклонить `pending`. Любая из двух сторон может отменить открытый запрос или завершить принятое наставничество. Другие сотрудники и HR не читают текст запроса через этот API. Самонаставничество запрещено; повторная открытая пара запрещена. Принятие блокирует строку профиля наставника, поэтому параллельные запросы не превышают capacity. Участники получают личные уведомления.

## Личные добровольные задания и достижения

| Метод и путь           | Тело / результат                                                   |
| ---------------------- | ------------------------------------------------------------------ | ------------- |
| `GET /me/tasks`        | Список личных заданий                                              |
| `POST /me/tasks` **I** | `{title, skillId?, targetLevel?:1..5, dueDate?:"YYYY-MM-DD"}`      |
| `PATCH /me/tasks/:id`  | `{status:"completed"                                               | "cancelled"}` |
| `GET /me/achievements` | `{visibility:"private", achievements, goalReady, pointsAwarded:0}` |

`skillId` и `targetLevel` задаются вместе. Задание по навыку нельзя завершить до достижения уровня в фактическом профиле. Обычное личное задание можно отметить выполненным вручную; оно не начисляет баллы. Достижения вычисляются из уникальных добровольных завершённых активностей (1, 5, 10) и текущих требований цели. Обязательные активности не учитываются. Публичных таблиц лидеров нет.

| Метод и путь                    | Доступ / тело                                                                     |
| ------------------------------- | --------------------------------------------------------------------------------- | ---------- | ------------ |
| `GET /colleagues?q=...`         | Поиск имени (2–80 символов), только ID, имя и подразделение                       |
| `GET /me/recognitions`          | Собственные отправленные и полученные благодарности, исключая скрытые модератором |

Нельзя благодарить себя. Благодарность изначально `pending`. Даже принятые благодарности видны только отправителю и получателю. Модератор видит текст только после жалобы. Благодарности не создают баллы. Личное уведомление не содержит текст благодарности.

## Командные учебные активности

| Метод и путь                        | Доступ / тело                                                          |
| ----------------------------------- | ---------------------------------------------------------------------- |
| `GET /team-challenges`              | Доступные сотруднику общие или командные активности                    |
| `POST /team-challenges` **I**       | Manager/HR/admin: `{title,description,startsOn,endsOn,eventIds:[...]}` |
| `POST /team-challenges/:id/join`    | Добровольное присоединение текущего сотрудника                         |
| `POST /team-challenges/:id/leave`   | Выход текущего сотрудника                                              |
| `POST /team-challenges/:id/archive` | Автор/HR/admin                                                         |

Активность руководителя доступна ему и его прямым подчинённым; HR/admin создаёт активность организации. Каталог ограничен активными добровольными мероприятиями. Вступление не записывает автоматически на все курсы — обычные prerequisites и правила записи сохраняются.

Возвращаются `memberCount`, агрегат `completedMembers`, собственный `joined` и собственное выполнение каждого мероприятия. Списков индивидуальной результативности и ранжирования нет. Групповое выполнение считается по реальным завершениям в интервале активности. Выход удаляет членство и участие в агрегате.

## Правила баллов, каталог и выдача наград

**По умолчанию всё отключено.** Каталог пуст для сотрудников до явного включения политики администратором. В систему не добавлены вымышленные материальные призы.

| Метод и путь                           | Доступ / тело                                                            |
| -------------------------------------- | ------------------------------------------------------------------------ | ------------- |
| `GET /admin/rewards/policy`            | Admin                                                                    |
| `PUT /admin/rewards/policy`            | Admin: `{enabled,pointsPerEvent:1..1000,monthlyCap:1..10000,rulesText}`  |
| `GET /admin/rewards/catalog`           | HR/admin: все награды                                                    |
| `POST /admin/rewards/catalog` **I**    | Admin: `{title,description,cost:1..100000,stock:number                   | null}`        |
| `PATCH /admin/rewards/catalog/:id`     | Admin: `{title,description,cost,stock,active}`                           |
| `GET /rewards/catalog`                 | Только активные позиции при включённой политике                          |
| `GET /me/rewards`                      | Собственные баланс, правила, ledger и redemptions; чтение без начисления |
| `POST /me/rewards/sync` **I**          | `{}`; сверяет реальные завершения и корректировки                        |
| `POST /me/rewards/redeem` **I**        | `{rewardId}`; сверяет начисления и атомарно резервирует награду          |
| `PATCH /me/rewards/redemptions/:id`    | `{status:"cancelled"}`; отмена своей невыданной награды                  |
| `GET /admin/rewards/redemptions`       | HR/admin: заявки на выдачу                                               |
| `PATCH /admin/rewards/redemptions/:id` | HR/admin: `{status:"fulfilled"                                           | "cancelled"}` |

### Начисление и защита от повторов

1. Начисляются только реальные завершения в приложении (`source_record_id IS NULL`) после включения политики. Учебная запись могла быть создана раньше; важен серверный момент перехода в `completed` (`reward_completed_at`). Импортированная история не даёт баллы.
2. За одно добровольное мероприятие сотрудник получает начисление один раз, включая повторяемый клуб. Обязательные мероприятия, личные задания, благодарности и вступление в команды не создают баллы.
3. Сумма выданных баллов в календарном серверном месяце ограничена `monthlyCap`. При достижении лимита оставшиеся завершения ожидают следующей сверки в следующем месяце. Обратная корректировка не освобождает лимит того же месяца для повторного фарминга.
4. Сумма и правило определяются сервером. Клиент не передаёт `delta`, баланс или стоимость; endpoint ручного начисления отсутствует.
5. `earned/reversed/redeemed/refunded` — неизменяемые записи ledger с уникальными ключами источника. Advisory lock по сотруднику сериализует сверку, списание и возврат. Строка каталога блокируется для защиты stock между разными сотрудниками.
6. Стоимость фиксируется в заявке в момент обмена. Позднейшее изменение каталога не меняет эту заявку. Повторное выполнение/отмена заявки не начисляет возврат ещё раз.
7. Если завершение исправлено или активность переведена в обязательные, сверка создаёт обратную проводку один раз. Если баллы уже потрачены, баланс может стать отрицательным; `spendableBalance=max(0,balance)` блокирует дальнейший обмен до погашения. История не переписывается.
8. Отключение политики запрещает новые начисления и обмен; обработка существующих заявок и сверка обратных корректировок остаются доступны. Повторное включение задаёт новый момент начала начислений.

`GET /me/rewards` возвращает `{enabled,balance,spendableBalance,rules,pointsPerEvent,monthlyCap,ledger,redemptions}`. Интерфейс при открытии кошелька вызывает отдельный `POST /me/rewards/sync` с CSRF и новым ключом, затем читает состояние. Перед каждым обменом сверка выполняется автоматически.

## Проверки

`tests/growth.test.ts` содержит pure-тесты сохранности исходных уровней, ограничения прироста, многошаговых prerequisites, времени, сессий, capacity и предпочтений. PostgreSQL-тесты создают случайную отдельную схему, запускают реальные миграции и импорт, затем проверяют приватность, права, идемпотентность, optimistic locking планов, согласие наставника, конкурентное принятие, модерацию, добровольность, конкурентные начисления/списания/возвраты и корректировку завершения. После выполнения схема удаляется.

```bash
cd Back
TEST_DATABASE_URL=postgresql://career_quest:career_quest_local_only@localhost:5433/career_quest \
  npx tsx --test tests/growth.test.ts
```

Эта строка использует локальные демонстрационные реквизиты из Compose. Для другого PostgreSQL задайте свой URL.
