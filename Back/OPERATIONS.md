# Эксплуатация, резервные копии и восстановление

## Что входит в поставку

- `infra/backup-demo.sh` — согласованный снимок локальной БД в custom-формате PostgreSQL.
- `infra/restore-demo.sh` — проверенное восстановление локальной демонстрации из такого снимка.
- `infra/reset-demo.sh` — возврат локальной демонстрации к исходному dataset, четырём demo-аккаунтам и 15 синтетическим статьям путеводителя.

Команды запускаются из корня репозитория. Нужны работающий Docker Compose, локальный Docker context и Python 3. PostgreSQL-клиенты берутся из контейнера `db`; устанавливать `pg_dump` на Mac не требуется. Скрипты совместимы с системным Bash macOS.

Эти команды работают с локальным Compose-проектом из `compose.yaml`. Они проверяют `DEMO_MODE=true`, соответствие backend своему `db`, loopback-порты, локальный `APP_ORIGIN`, локальный Docker Unix socket и принадлежность запущенного контейнера этому workspace. Rendered Compose-конфигурация разбирается в памяти; `DATABASE_URL`, пароли и API-ключи не печатаются.

## Резервная копия локальной демонстрации

```bash
docker compose up -d db
./infra/backup-demo.sh
```

Команда выводит путь к файлу, например `backups/career-quest-20260923T120000Z-12345.dump`. Можно задать отдельный файл:

```bash
./infra/backup-demo.sh backups/before-presentation.dump
```

Backup — операция чтения; подтверждающий флаг для неё не нужен. `pg_dump --schema=public` создаёт согласованный снимок приложения даже при его работе. Изолированные схемы автоматических тестов и другие схемы не включаются. Снимок записывается сначала во временный файл, проверяется через `pg_restore --list`, затем переименовывается. Существующий файл не перезаписывается. Рядом сохраняется SHA-256 (`.dump.sha256`). Права файлов — `0600`, umask — `077`; `/backups/` исключён из Git.

Снимок содержит профили, аккаунты с хешами паролей, историю, диалоги и интеграционные данные. Доступ к нему должен быть ограничен так же, как к БД. Переносите копии через утверждённое защищённое хранилище; локальный файл не защищает от потери самого Mac. Пароли окружения и OpenAI-ключ в dump не включаются, поскольку не хранятся в таблицах.

## Возврат к исходному тестовому состоянию — DATA-07

```bash
./infra/reset-demo.sh --replace-local-demo
```

Без точного флага команда завершится до обращения к БД. Порядок:

1. Проверить локальную конфигурацию и отсутствие оплаченного/неопределённого AI-ledger.
2. Собрать актуальные образы `back` и, если объявлен, `worker`.
3. Создать временную БД с уникальным именем `cq_demo_stage_<UUID>`.
4. Применить все SQL-миграции, выполнить CLI `seed`. Он импортирует исходный пакет и в demo-режиме создаёт аккаунты и путеводитель.
5. Проверить данные: 200 сотрудников, 60 навыков, 40 мероприятий, 2743 записи истории, 4 demo-аккаунта, 15 синтетических статей для чистого reset.
6. Полностью подготовить SQL восстановления до изменения рабочей БД.
7. Остановить ранее работавшие `front`, `back`, `worker`; создать **ещё одну backup-копию текущего состояния** `backups/before-reset-…dump`.
8. Заменить схему `public` одной транзакцией PostgreSQL. Ошибка внутри восстановления откатывает и DDL, и данные.
9. Запустить ранее работавшие сервисы, удалить временную БД и промежуточный SQL-файл.

Схема `public` содержит всё состояние приложения. Другие схемы этой БД скрипты не сбрасывают. Записи пользователей, новые цели, учебные планы, участия, диалоги, настройки и статьи текущей демонстрации заменяются исходным состоянием; прежнее состояние остаётся в backup-файле. Активные сессии после сброса отсутствуют — войдите заново.

Если БД проверяется с помощью дополнительных вручную запущенных процессов, завершите их до reset: скрипт останавливает только сервисы Compose этого проекта, а не произвольные процессы на Mac. Скрипт не запускает внешний ИИ, webhooks, NVIDIA или другие платные ресурсы.

## Восстановление локальной демонстрации из backup

```bash
./infra/restore-demo.sh --replace-local-demo backups/before-presentation.dump
```

Используйте backup, созданный вашим проектом: PostgreSQL-архив содержит исполняемые определения объектов БД. Если рядом есть `.sha256`, контрольная сумма проверяется; сам формат архива проверяется всегда.

Сначала схема `public` из архива восстанавливается через `pg_restore --schema=public` в отдельную временную БД. На ней выполняются текущие миграции и идемпотентный demo-seed, проверяется наличие исходного dataset/демо-материалов. Дополнительные профили и сохранённые действия из backup остаются. Неактуальные версии миграций и ошибки данных останавливают процесс **до замены рабочей БД**.

Затем выполняется тот же порядок остановки сервисов, backup текущего состояния и транзакционной замены `public`. В backup восстановления остаётся файл `before-restore-…dump`. Сессии из восстанавливаемой БД принудительно отзываются, чтобы старые cookies не становились действующими снова. После восстановления нужно войти заново.

Даты исходного dataset остаются синтетическими: дата расчёта `2026-10-01`. Сроки сессий, аудит и срок проверки статей используют реальное время. Восстановление старой backup не продлевает утверждение статьи или контакта.

### Защита финансового журнала

Для reset/restore необходимы `AI_ENABLED=false` и `WORKER_DELIVERY_ENABLED=false` в конфигурации сервисов. Замена блокируется, если текущая либо восстановленная БД содержит оплаченные или незакрытые записи `ai_usage`. Иначе восстановление старого снимка могло бы уменьшить учтённый расход и снова открыть уже потраченный бюджет. Обычный backup такого состояния разрешён.

Если уже использовался платный OpenAI, выполняйте контролируемое восстановление с сохранением финансового журнала и сверкой с провайдером по процедуре ниже. Не удаляйте записи расходов для обхода ограничения.

### Ошибки и повторный запуск

- Ошибка подготовки/миграции временной БД оставляет рабочее состояние прежним.
- Ошибка SQL-замены откатывает `public` полностью; backup также остаётся.
- Если ошибка произошла после остановки приложения, скрипт оставляет сервисы остановленными и выводит путь recovery-backup. Проверьте причину, затем используйте `docker compose up -d`.
- Если замена уже зафиксирована, но сервисы не запустились, скрипт сообщает это отдельно. Проверяйте `docker compose ps`, логи `back`/`worker` и readiness, прежде чем повторять операцию.
- Временная БД удаляется обработчиком завершения только по сгенерированному имени. Если соединение с Docker оборвалось, в сообщении остаётся её точное имя для ручной очистки. Не удаляйте `career_quest` и Docker volume для такой очистки.

## Миграции и обновление приложения

Файлы `Back/db/migrations/*.sql` после применения неизменяемы. CLI хранит SHA-256 каждой миграции в `schema_migrations`; редактирование старого файла вызывает ошибку. Исправления добавляются новым номером миграции. Не изменяйте checksum в таблице, чтобы скрыть расхождение.

Обычный локальный update сохраняет данные:

```bash
./infra/backup-demo.sh
docker compose build back worker
docker compose run --rm --no-deps back node dist/src/cli.js migrate
docker compose up -d back worker front
```

В конфигурациях без отдельного `worker` уберите его из команды. `migrate` не является reset; `seed` идемпотентен для исходного пакета, но предназначен для демонстрационного окружения. Порядок миграций и совместимость версий приложения необходимо проверить в тестовой БД перед внешним развёртыванием.

## Внешнее окружение: backup и контролируемое восстановление

Локальные demo-скрипты намеренно не запускаются против удалённого Docker или production-настроек. Для внешнего окружения используйте его утверждённое хранилище secrets, механизм backup и контроль доступа. Минимальная процедура:

1. Определить требуемую глубину хранения и допустимую потерю данных; настроить регулярный `pg_dump` и/или резервирование с WAL/PITR средствами оператора PostgreSQL.
2. Хранить зашифрованную копию отдельно от хоста БД, ограничить доступ, записывать контрольную сумму и версию приложения/миграций. Регулярно восстанавливать копию на отдельном экземпляре PostgreSQL; наличие файла само по себе не подтверждает работоспособность backup.
3. Перед восстановлением остановить приём изменений, worker и внешнюю доставку. Сделать финальную копию текущей БД и отдельно зафиксировать актуальный AI-ledger, платёжную сверку и журналы внешних операций.
4. Развернуть **новую БД** на PostgreSQL совместимой версии. Восстановить доверенный архив через `pg_restore --no-owner --no-acl --exit-on-error --single-transaction`; назначить владельцев/права по утверждённой схеме окружения.
5. Подключить миграционный процесс к новой БД через secret-конфигурацию и выполнить `node dist/src/cli.js migrate`. **Не запускать demo-seed** и не включать `DEMO_MODE`.
6. Проверить количество и связи записей, дату snapshot, доступ всех ролей, журнал миграций и readiness. Отозвать восстановленные сессии. Проверить действительность контактов и материалов с учётом текущего времени.
7. Сопоставить `ai_usage` с более новым pre-recovery журналом и расходами провайдера. Незакрытые резервы учитывать консервативно. Разрешить OpenAI только после восстановления полного расхода; общий лимит не должен уменьшиться из-за старого снимка.
8. Сверить внешние заявки/webhook receipts и idempotency-ключи с внешними системами. Не возобновлять доставку до исключения повторных побочных действий.
9. Переключить приложение на новую БД. Проверить HTTP-сценарии и метрики. Затем отдельно включить worker/интеграции. Сохранить старую БД и recovery-backup на согласованный срок для отката.

Пароли и API-ключи не передаются в URL командной строки и не публикуются в логах. Конкретное расписание backup, шифрование, внешнее хранилище и production-права зависят от выбранной инфраструктуры; этот репозиторий не создаёт их автоматически.

## Проверка поставленной процедуры

В ходе реализации выполнено без замены рабочей БД:

- `bash -n` для трёх скриптов; проверка справки и обязательного подтверждающего флага.
- Backup текущей синтетической БД через `pg_dump`, проверка `pg_restore --list`, SHA-256 и прав файла.
- Восстановление в отдельную БД `cq_restore_test_<UUID>` того же локального PostgreSQL-контейнера.
- Все текущие миграции и demo-seed на этой временной БД: **200 сотрудников, 60 навыков, 40 мероприятий, 2743 участия, 4 demo-аккаунта, 15 статей**.
- Проверка транзакционности: намеренная ошибка в конце SQL замены сохранила прежние записи и тестовую таблицу; успешная замена сохранила все ожидаемые количества и удалила прежнюю тестовую таблицу.
- Удалена только созданная проверкой временная БД. Рабочая БД использовалась для чтения backup; reset/restore против неё не выполнялись.
